Gathering logs and reporting bugs

A report with the right log attached is usually answered. One without it usually turns into a conversation about how to produce it. This page is that conversation, written down once.

The one command worth knowing

journalctl is the system's log. Almost every question about "why did that fail" is answered by one of these: 

journalctl -b            # everything since this boot
journalctl -b -1         # the boot before this one, useful after a crash
journalctl -b -p err     # only errors, which is usually enough
journalctl -u sddm       # one service
journalctl -f            # follow, while you reproduce the fault

Inside it, arrow keys and Page Up/Down scroll, / searches, G jumps to the end, and q quits.

Kernel messages

For hardware that is not detected, firmware that failed to load, or a disk throwing errors, the kernel ring buffer is the place to look: 

sudo dmesg -T | tail -50
sudo dmesg -T | grep -i -E 'firmware|error|fail'

What changed recently

On a rolling release this is often the whole answer: 

grep -E 'upgraded|installed' /var/log/pacman.log | tail -40

The Update Center shows the same history with restore points beside it, which is easier to read and lets you act on it.

Something specific to SakuraOS

The parts we wrote log to the journal like anything else: 

journalctl -u sakura-updates          # the nightly update run
journalctl -u sakura-boot-success     # the failed-boot watchdog
journalctl -u sakura-kernel-sync      # boot image vs installed kernel
journalctl -t sakura-install          # the installer, on the live media

The recovery environment prints to the screen rather than the journal, because at that point there is no journal to write to. A photograph of it is a legitimate bug report.

A program that will not start

Run it from a terminal. Almost everything prints the reason and then exits, and that line is worth more than any description of the symptom: 

sakura-store 2>&1 | tail -20

What to include in a report

Four things, and it does not need to be more than a few lines:

  • What you did, what you expected, and what happened instead.
  • Whether it started after an update, and which one, from the history above.
  • The relevant log, pasted as text rather than a screenshot where possible.
  • Your hardware, if it is a hardware fault: inxi -Fxz gives a tidy summary with serial numbers stripped.

Check what you are pasting. A journal can contain network names, hostnames and paths that include your name. inxi -Fxz strips identifiers; journalctl does not.

Where to send it

  • Bugs in SakuraOS itself, meaning the installer, the store, the Update Center, Terminal Assist, Settings or the recovery environment: the issue tracker in the repository.
  • Questions and things that might not be bugs: r/SakuraOS.
  • A package that is broken upstream, meaning it behaves the same on plain Arch: report it to Arch or to the package's own project. Our nightly canary catches many of these first and holds the package back, so it is worth checking whether the Update Center already lists it as held.

Security problems

If you have found something with security consequences, please do not open a public issue for it. Send it privately through the contact address in the repository, describe the class of problem, and give the maintainers a chance to fix it before it is public.
